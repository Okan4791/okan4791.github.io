Problem

Dynamic DNS APIs agree on the goal, not the protocol.

Providers differ in authentication, record lookup, response shape, and dual-stack behavior. A useful updater also has to distinguish a real IP change from a temporary discovery failure.

Running several accounts adds another constraint: one failed host should not force successful hosts through the same update again.

Decision

Keep the loop small and move variation behind provider contracts.

Each provider implements one registered update interface. Configuration is schema-validated, unsupported keys fail early, and each host receives an independent atomic checkpoint.

Public-IP and provider requests use pin-on-connect HTTPS. The client rejects loopback, link-local, metadata, and private destinations by default, then connects only to the verified address set. Transient failures use bounded retry with jitter and honor Retry-After.

Result

One operational model across fifteen provider families.

The same core supports a long-running daemon, one-shot CLI calls, Docker deployments, and optional MCP transports. Multi-account YAML can also define ordered failover for hostnames served by more than one DNS provider.

Documentation-contract tests keep provider IDs, defaults, commands, and security allowlists aligned with the implementation.
